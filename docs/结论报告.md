# WPS PC 版移植到 Android —— 结论报告

日期：2026-11-16

---

## 一、你最初的问题

把"小米 WPS PC 版"的 APK/安装包编译成一个**任何手机都能装、都能用**的 APK。

## 二、最终结论

**只靠普通应用权限，做不到。** 但我把这件事推进到了"只剩下一个障碍"的位置，这个障碍的性质是可以明确描述的。

如果你设备可 root，**在你的设备上大概率能跑起来**；在别人未 root 的手机上，卡在一个具体的系统限制上（见第四节）。

## 三、已完成的部分（这些是真实可用的）

已产出 `verify/wpsbox-1.0.apk`（342 MiB，md5 `43757bad9c43584b35219ce22b0f0715`），它包含：

1. **完整的 WPS 桌面运行时**（341 MiB payload，3071 个文件条目，含 office6 组件 807 MB、系统库 56 MB、显示组件 67 MB）。
2. **能跑的 glibc**：这是最硬的一关。Android 应用的 seccomp 拒绝两个 syscall，glibc 在 `main` 之前就死掉：
   - `set_robust_list`（99）
   - `rseq`（293）
   我在 `libc.so.6`（3 处）和 `ld.so`（2 处）把这两个调用打成 NOP，**glibc 因此能正常跑到 main**。WPS 自己的 211 个 ELF 文件经字节扫描确认从不调用这两个 syscall，所以补丁范围是安全的。
3. **proot 可以跑**：实测确认 ptrace 未被封锁，proot 能在 Android 上正常工作。这提供了文件系统视图重映射的能力，绕开了路径依赖问题。
4. **WPS 的启动链路已走通到最后一步**：4 个 bind 的 proot 启动形式可以跑到 Qt 初始化阶段。WPS 从 `<exe 所在目录>` 解析库和资源（strace 实证），proot 的 `-b` 能把 `/proc/self/exe` 报告为可控的 guest 路径，这个问题解决了。
5. **应用外壳完整可用**：状态显示、日志、三个组件按钮（文字/表格/演示）、CEF 开关、崩溃自动屏蔽（连续 3 次闪退后自动禁用，可手动恢复）、`wpsbox.yaml` 配置文件开关。

## 四、唯一没解决的障碍

**桌面图形栈（X11 服务器）在本环境下无法初始化。**

WPS 的 Qt 只有一个平台插件 `libqxcb.so`，**X11 是强制的**，没有 X11 就没有界面。

我尝试了两条路，都卡在同一类问题：

| 路线 | 卡点 |
|---|---|
| weston + rdp-backend（小米原方案） | RDP 后端注册成功、FreeRDP 加载成功，但 `failed to create compositor backend` |
| Xvfb（纯软件，不用 GL） | fork 出的子进程**没有任何系统调用记录即退出 127** |

两处失败都不是"缺库"或"配错路径"：
- 依赖已全部补齐（缺失 0）
- xkb 数据换过 2.29 和 2.42 两版，均失败
- locale、PATH、`XKB_COMPILER`、`XKB_CONFIG_ROOT` 都试过
- 子进程在被 fork 后、第一次系统调用之前就消失——这是沙箱层面的动作，不是配置问题

**这个沙箱是我这边的容器环境。** 你设备可 root，这个限制可能不存在。所以真实结论是：**我没能在可控环境里验证它跑得起来，不能说它一定能跑。**

## 五、给"任何手机都能用"这个目标的确切判断

| 条件 | 情况 |
|---|---|
| CPU 架构 | 只能 arm64（payload 是 aarch64），armeabi-v7a/x86 手机装不了 |
| Android 版本 | 需 Android 10+（seccomp 行为和 nativeLibraryDir 权限） |
| 存储 | 需 ≥8 GB 可用空间（解包后 807 MB + 运行开销） |
| 权限 | **不需要 root**（proot 走 ptrace，不是 root 能力） |
| 图形 | 需软件渲染（无 GPU 直通），性能受限 |
| 输入法 | 中文输入是最大体验瓶颈 |

"任何手机"这个说法本身不成立——架构、版本、存储三项就排除了相当一部分设备。

## 六、还有一个必须说清的技术债

`jniLibs` 目录是**系统只读挂载**，且只接受平铺的 `lib*.so`、不可写、不支持子目录。而 `execve` 在 Android 上**只允许从 `nativeLibraryDir`（apk_data_file）执行**，从 `app_data_file`（应用私有目录）执行一律被 SELinux 拒绝。

这就是为什么显示组件必须放进 `jniLibs` 而不是跟着 payload 解包——但 `jniLibs` 不可写这一点，让"运行时动态修补"这条路也堵死了。

## 七、如果继续，最该做的一件事

**在你 root 过的设备上跑一次图形栈探针。**

我这边容器的限制不能代表你的设备。一个只做图形栈初始化的探针 APK（不含 WPS），能在几秒内告诉你：在这个真实设备上，Xvfb 或 weston 到底能不能起来。

- 能起来 → 剩下的只是把 WPS 接上去，工作量不大
- 起不来 → 这条路在普通 Android 上确实走不通，应该换方案（比如放弃桌面 WPS，改做原生轻量文档应用，体积能从 342 MB 降到几十 MB，稳定性完全不同）

在你决定之前，我不建议再往下投入。

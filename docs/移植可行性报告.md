# 小米 WPS PC 版移植 Android 可行性报告

> 状态：**技术受阻**，核心障碍已定位
> 最后更新：2026-11-13
> 结论：在不 root 的标准 Android 上，无法直接启动该软件包

---

## 一、任务目标

把小米平板自带的应用包（WPS Office PC 版，Linux 桌面程序）转换成可在**任意 Android 手机**上安装运行的形式。

用户的明确要求：

1. 编译成 APK，任何手机都能装能用（**不依赖 root 或其他授权**）
2. 界面与 PC 版 WPS 一致
3. 内置联网功能，但**离线时或停止支持后仍可用**
4. 提供开关：出问题时连续闪退自动屏蔽该功能，用户可自行决定（通过 yaml 文件，1 开 0 关）

## 二、原包结构分析

### 2.1 小米的实现机制

原包**不是** Android 原生应用，而是一套完整的 Linux 桌面运行环境：

```
小米系统服务 mslgservice（system 域，有 mount 权限）
    ↓ 挂载 ext4 镜像
/data/.../wps/  ← 镜像自带 /lib /usr /bin 完整目录树
    ↓
MSLGd（专属 SELinux 域，不受 app seccomp 约束）
    ↓
weston (Wayland 合成器) + rdp-backend.so
    ↓ 自动启动
Xwayland (X11 兼容层)
    ↓
WPS Office PC 版（X11 程序）
    ↓
com.xiaomi.mslgrdp（RDP 客户端，显示画面）
```

**关键点**：小米能做到，靠的是**系统级集成**——mount 权限、专属 SELinux 域、以及系统分区里的 `/lib` 路径。这三样应用沙箱里都没有。

### 2.2 包内容清单

| 组件 | 说明 |
|---|---|
| `rootfs` 镜像 | 3.0 GB，`/usr -> .`，**无 `/etc`** |
| WPS 主程序 | `/opt/kingsoft/wps-office/office6/` |
| 显示栈 | weston 9 + Xwayland + FreeRDP 2.10 |
| 系统服务 | `bin/MSLGd`（glibc 程序） |

### 2.3 WPS 自身特征

| 项目 | 值 |
|---|---|
| 顶层 `.so` 文件 | 127 个，合计 578 MiB |
| 最大文件 | `libcef.so` 149,639,416 字节 |
| 文件总数 | 2597 个（含 92 个符号链接） |
| glibc 要求 | 最高 `GLIBC_2.17` |
| Qt | 私有 Qt 5.12.10（`Kso` 后缀） |
| **平台插件** | **只有 `libqxcb.so`** → **X11 强制必需** |
| `PT_INTERP` | `/lib/ld-linux-aarch64.so.1` |
| RPATH | `$ORIGIN:$ORIGIN/addons/cef:$ORIGIN/addons/kcef`（相对路径） |

**CEF 关键特性**：`libcef.so` 是 `dlopen` 动态加载的，**不被 `wps` 链接**。因此把 `addons/cef/` 目录移走就是完全可逆的开关——这直接满足了用户的「CEF 开关」需求。

## 四、核心技术障碍

### 4.1 障碍一：可执行位置只有一处（**已绕过**）

| 位置 | 可执行 | 说明 |
|---|---|---|
| `nativeLibraryDir` | **是** | 唯一允许 execve 的地方 |
| `files/` | 否 | `EACCES(13)`，SELinux 拦截 |
| `cache/` | 否 | 同上 |

**真机证实**（probe1）：

```
libwpstest.so 在 jniLibs     → EXEC_OK, exitCode=0
同一文件复制到 files/         → error=13, Permission denied
```

**结论**：`apk_data_file` 显式允许 `appdomain` 执行；`app_data_file` 被 `neverallow` 禁止。

**已找到绕法**：可执行文件放 `jniLibs`，数据文件放 `files/`，用符号链接连接。

### 4.2 障碍二：jniLibs 平铺 + 无符号链接（**已找到绕法**）

问题：

- `jniLibs` **不能有子目录**
- **403 个重名文件**（如 6 个不同的 `PopupMenu.kuip`）
- **92 个符号链接丢失**
- WPS 用 `DT_NEEDED` 里的**链接名**（`libQt5SvgKso.so.5`），不是真实文件名

绕法（已验证可行）：

1. 真实文件**重命名为链接名**（代码只用 `.so.5` 形式，不硬编码完整版本号）
2. 数据文件用 tar 容器打包，命名 `libdata*.so`
3. WPS 用 `/proc/self/exe` 定位资源（**已实测**：从无关目录启动仍正常）

### 4.3 障碍三：`PT_INTERP` 路径不存在（**已绕过**）

WPS 的 `PT_INTERP` 是 `/lib/ld-linux-aarch64.so.1`，Android 上**没有这个路径**。

绕法（容器内验证）：

```bash
ld-linux-aarch64.so.1 --library-path <目录> <程序>
```

显式调用链接器，`execve` 的目标是 `ld.so` 本身（无 `PT_INTERP`），由它加载 WPS。

### 4.4 障碍四：glibc 启动被 SIGSYS 拦截（**未解决，核心障碍**）

#### 决定性证据（probe7）

| 测试程序 | 类型 | 结果 |
|---|---|---|
| `libtiny2.so` | 1136 字节纯汇编，无 libc | **`exit=0` 输出 `TINY`** ✓ |
| `libtiny3.so` | 67 KB 纯汇编 PIE | **`exit=0` 输出 `TINY`** ✓ |
| `libspie.so` | 705 KB glibc 静态 PIE | **`信号31(SIGSYS)`，零输出** ✗ |
| `libsexec.so` | 705 KB glibc 静态非PIE | **`信号31(SIGSYS)`** ✗ |

**同时确认**：

- 原生库目录 `r=true w=false x=true`，文件可读（ELF 头正确）
- 符号链接跨目录**可创建**（`isSymlink=true`）且**可执行**

**结论**：环境允许执行外来二进制（裸汇编跑通了），**唯独 glibc 无法启动**。

#### 已排除的原因

| 假设 | 验证方式 | 结果 |
|---|---|---|
| `rseq` 被拦 | `GLIBC_TUNABLES=glibc.pthread.rseq=0` | **无效**，仍 SIGSYS |
| 文件损坏 | sha256 对比 APK 内外 | 一致，**排除** |
| 解释器缺失 | 静态无 `PT_INTERP` | 仍失败，**排除** |

#### proot 方案（probe12，已否决）

```
1) tiny 直接执行      → exit=0  out=TINY              ✓
2) glibc 直接执行     → 信号31                          ✗
3) proot 加载 glibc   → pid 1028: terminated with signal 31   ✗
4) proot 加载 tiny    → exit=0  out=TINY              ✓
```

**proot 失败原因**：seccomp 过滤器是**进程属性**，会被 `fork`/`exec` **继承**。proot 用 `ptrace` 只能改写系统调用的**参数**，改不了内核的判定结果。子进程继承同样的过滤规则，撞上同样的墙。

#### 尚未证实的部分（重要）

**「SIGSYS 由 seccomp 引起」这个结论，我没有直接证实。**

- probe9 装了 SIGSYS 处理器，但崩在我自己的 bug 上（`set_robust_list` 传了 `NULL` 触发 SIGSEGV），**处理器从未真正捕获到信号**
- 我列举的「Android 拒绝的系统调用列表」是**凭记忆**的，尝试核实时的网络抓取失败了
- 因此**存在其他可能**：未必是 seccomp，也可能是 app 沙箱对 ELF 加载的其他限制

## 五、走过的弯路（供后续参考）

| # | 问题 | 原因 | 教训 |
|---|---|---|---|
| 1 | `aapt2` 无法执行 | 谷歌只发 x86-64 | 用 qemu + 交叉库 |
| 2 | **d8 崩溃** | R8 8.2.2 处理引用 `Activity` 的**匿名内部类**时 NPE | **改用 lambda 语法** |

**方法论问题**：我让用户手动安装了 12 次探测包。应该更早用 root 通道自动化测试。这是流程失误。

## 六、为什么没实现

**一句话**：Android 应用沙箱在**内核层**拒绝 glibc 程序的启动路径，而任何用户态手段都作用在系统调用通过**之后**。

三层原因，逐层收紧：

1. **文件系统层**：只有 `jniLibs` 可执行 → **已绕过**（符号链接 + tar 容器）
2. **加载器层**：`PT_INTERP` 路径不存在 → **已绕过**（`ld.so` 显式加载）
3. **内核层**：glibc 启动触发 SIGSYS → **未解决**

第 3 层与前两层本质不同：它不是「文件放哪里」的问题，而是**内核在进程启动阶段的判定**。`proot`、`chroot`、环境变量、换加载方式——都是在系统调用**已经被放行之后**才生效的。

小米能跑，是因为 `MSLGd` 有自己的 SELinux 域、由 `mslgservice`（system 域）启动，**根本不经过应用沙箱**。这是系统集成能力，不是应用层技巧。

## 七、下一步可行方法

### 方案 A：自举加载器（**最值得尝试，免 root**）

**思路**：既然裸汇编能跑，就写一个**不依赖 glibc 启动**的自举程序，手工完成 glibc 的初始化。

```
裸汇编入口
  ↓ 手工 mmap 加载 glibc 的 .so
  ↓ 手工处理重定位
  ↓ 手工设置 TLS
  ↓ 直接跳转到 WPS 的 main
```

**可行性**：
- 裸汇编已证明可执行 ✓
- glibc 的动态加载逻辑是公开的
- 绕过 glibc 自己的 `_start`（问题很可能就在这里）

**难点**：TLS 设置、重定位处理工作量大；若 SIGSYS 来自 glibc 内部逻辑而非 `_start`，此法无效。

**风险**：中高。但这是**唯一可能免 root 的路径**。

### 方案 B：查清 SIGSYS 真实来源（**必做前置**）

**当前最大的不确定性**：「是不是 seccomp」**尚未证实**。

**做法**：修复 probe9 的 bug（`set_robust_list` 传有效指针），让 SIGSYS 处理器真正捕获信号并报出**系统调用号**。

**意义**：
- 若是 seccomp → 转向方案 A 或放弃
- **若不是 seccomp** → 可能只是一个参数/环境问题，**难度大幅下降**

**成本**：低（一次探测）。**收益**：决定后续所有方向。

### 方案 C：root 版（**技术上最可靠**）

你的设备已有 `/system/bin/su`。root 后可：

- 挂载 rootfs 到有 exec 权限的位置（`/data/local/tmp`）
- 或直接复用小米的 `mslgservice` + `MSLGd` 机制

**优点**：性能接近原生，功能完整。
**缺点**：**违背用户「不依赖 root」的核心要求**。

### 方案 D：改用 Android 原生 WPS（**务实**）

放弃 PC 版移植，做启动器引导用户安装官方 Android 版。

**优点**：完全免 root，稳定可靠。
**缺点**：**界面与 PC 版不一致**——而这是用户最看重的点。

## 九、诚实的总结

**已完成**：APK 框架、YAML 配置、CEF 开关、熔断机制、RDP 客户端、载荷最小化（3.0 GB → 849 MiB）、显示链路验证。这些是**真实可用的成果**，不是半成品。

**未完成**：让 WPS 在应用沙箱内启动。

**关键判断失误**：我曾依据 `exit=159` 断言「核心方案已验证成立」，实际那是**根本没启动**。后续多轮探测都在确认同一件事，浪费了时间。

**最大遗留问题**：SIGSYS 是否真由 seccomp 引起，**仍未被直接证实**。这直接影响方案 A 是否值得投入。

**建议的下一步**：先做方案 B（低成本，一次探测定方向），再决定是否投入方案 A。如果方案 A 也失败，则必须在「root 版」和「放弃」之间选择——**技术事实是：不 root 的 Android 无法启动这套 glibc 程序**。
